# Davas 고가치 화면·플로우 구현/재검증 Codex 프롬프트 쌍

**작성일:** 2026-07-11  
**AS-IS 서비스:** <https://davas.duckdns.org/>  
**작업 TODO:** [davas-high-value-screen-flow-todo.md](./davas-high-value-screen-flow-todo.md)

## 1. 사용 방법

1. 먼저 **프롬프트 A — 전체 구현 작업용**을 새 Codex 작업에 그대로 붙여 넣는다.
2. 프롬프트 A가 완료되면 가능하면 별도 Codex 작업에서 **프롬프트 B — 재검수·재검증·재작업용**을 실행한다.
3. 프롬프트 B는 분석 보고서만 만드는 프롬프트가 아니다. 미구현·부분구현·잘못된구현·불필요구현을 근거로 분류한 뒤, 권한과 작업 범위 안에서 직접 재작업하고 다시 검증해야 한다.
4. 두 프롬프트 모두 배포된 AS-IS 서비스를 **읽기 전용 시각·동작 기준**으로만 사용한다. 운영 데이터 생성·수정·삭제와 배포는 사용자의 별도 명시적 요청 없이는 수행하지 않는다.

## 2. 2026-07-11 AS-IS 관찰 기준

로그인하지 않은 상태에서 배포 서비스를 읽기 전용 확인한 결과다. 실행 시점의 서비스가 달라졌을 수 있으므로 각 프롬프트가 시작할 때 다시 확인한다.

- `/` 접근 시 `/login`으로 이동한다.
- 로그인 화면은 옅은 회청색 배경, 중앙의 흰색 모바일 카드, Davas 로고, 진한 청색 제목, coral 계열 주요 CTA, 둥근 입력과 부드러운 그림자를 사용한다.
- 로그인 화면에 이메일, 비밀번호, 비밀번호 보기, 로그인 상태 유지, 비밀번호 찾기, Google, Apple, 회원가입 진입이 노출된다.
- 현재 비밀번호 찾기는 `#` 링크이며 Google·Apple 버튼은 TODO 기준으로 실제 동작 여부를 재검증해야 한다.
- `/signup`에는 닉네임, 이메일, 비밀번호, 비밀번호 확인, 약관 동의가 있고 초대 코드 단계는 없다.
- 보호 화면은 인증 없이는 관찰할 수 있으므로, 필요하면 사용자가 브라우저에서 직접 로그인하도록 요청하고 로그인 후에도 운영 데이터를 변경하지 않는 읽기 전용 탐색만 수행한다.

AS-IS는 다음 용도로 사용한다.

- 기존 브랜드·색상·밀도·카드·여백·모바일 셸의 기준
- 현재 사용자 동선과 문구의 비교 기준
- 변경 전후 시각 회귀와 의도하지 않은 UI 이탈 확인

AS-IS의 비동작 버튼, 잘못된 공개 범위, 접근성 문제, 상태 모순은 보존 대상이 아니다.

## 3. 기준 우선순위

기준이 충돌하면 다음 순서로 판단한다.

1. 개인정보·권한·데이터 무결성·완료 조건이 명시된 `davas-high-value-screen-flow-todo.md`
2. `davas-pwa-self-hosted-design.md`의 모바일 우선·초대제·기록 우선·친구 기반 제품 원칙
3. 저장소의 실제 API 계약, 데이터 모델, 테스트, 마이그레이션 제약
4. 배포된 AS-IS 서비스의 시각·상호작용 기준

즉, AS-IS의 시각적 정체성은 유지하되 TODO가 수정 대상으로 지목한 AS-IS 결함은 그대로 복제하지 않는다.

## 4. 프롬프트 A — 전체 구현 작업용

```text
당신은 D:\Projects\davas 저장소의 Davas 모바일 우선 PWA를 실제로 완성하는 구현 담당 Codex다.

절대 원칙:
1. 먼저 위 문서들을 끝까지 읽고 AGENTS.md, git status, 현재 라우트, API, 엔티티, 마이그레이션, 테스트를 조사한다.
2. 사용자의 기존 변경과 untracked 파일을 보존하고, 관련 없는 파일을 되돌리거나 정리하지 않는다.
3. 배포된 AS-IS 서비스는 브라우저로 읽기 전용 확인한다. 운영 폼 제출, 데이터 생성·수정·삭제, 계정 생성, 배포는 별도 허가 없이는 하지 않는다.
4. 인증이 필요한 AS-IS 화면을 확인해야 하면 사용자에게 브라우저에서 직접 로그인해 달라고 요청한다. 비밀번호나 토큰을 요구·추출·기록하지 않는다.

7. 현재 Next.js + NestJS + TypeORM + PostgreSQL 구조를 유지한다. 기술 교체 자체를 목표로 삼지 않는다.
8. 공개 대규모 SNS로 확장하지 않는다. PRIVATE/FRIENDS/SELECTED, 같이 본 기록, watchlist, 친구 피드가 MVP 핵심이다.
9. TODO 체크박스는 코드가 존재한다는 이유만으로 완료하지 않는다. UI/API/DB/권한/상태/테스트/직접 URL 검증이 완료된 항목만 [x]로 갱신한다.
10. 테스트를 통과시키기 위해 실제 요구사항을 약화하거나 테스트를 무의미하게 만들지 않는다.

기준 충돌 우선순위:
1) TODO의 개인정보·권한·데이터 무결성·완료 조건

1단계 — AS-IS 및 저장소 기준선 확보:

- apps/web, apps/api, packages/shared, docker-compose, deployment 문서와 테스트를 조사한다.
- TODO 167개 체크박스를 구현됨/부분구현/미구현/선행결정필요로 초기 매핑한다.
- docs/product/davas-high-value-screen-flow-implementation-status.md 에 초기 상태, 의존성, 작업 순서를 기록한다.

2단계 — P0를 먼저 완성:

P0-01 공개 범위와 개인정보:
- 새 기록 기본값을 PRIVATE로 변경한다.
- PRIVATE/FRIENDS/SELECTED 데이터 모델, shared type, DTO, API, UI를 일치시킨다.

- 기록 상세·목록·검색·피드·댓글·반응이 동일한 서버 권한 판정을 사용하게 한다.

P0-02 첫 기록 작성:

P0-03 허위 조작 제거:

- 이번 MVP에 구현하지 않을 기능은 숨기거나 명확한 disabled/준비중 상태로 바꾼다.
- href="#", 빈 onClick, 전달되지 않은 action prop이 활성 UI에 남지 않게 한다.

P0-04 상태 설계:
- 주요 route에 loading/error/not-found 상태를 구현한다.
- loading/success-empty/success-data/error가 상호 배타적으로 렌더링되게 한다.
- 인증 실패, 권한 실패, 네트워크 실패, 서버 실패를 구분한다.
- 부분 실패는 성공한 데이터를 보존하고 해당 영역만 재시도할 수 있게 한다.
- 저장·수정·삭제의 pending과 중복 제출 방지를 구현한다.

P0-05 모바일·내비게이션·접근성:
- 360/390/430px에서 다이어리 요약, 캘린더, 장르 비율을 검증하고 과밀 레이아웃을 수정한다.
- 터치 대상 44px, focus-visible, WCAG AA 대비를 적용한다.
- /diary/*와 /profile/*에서 상위 bottom tab 활성 상태를 유지한다.
- drawer와 modal에 inert/aria-hidden, Escape, 최초 포커스, trap, restore를 구현한다.
- 자동 캐러셀 정지와 prefers-reduced-motion, 별점 키보드 조작을 구현한다.

P0 완료 전에는 P1의 시각 확장에 우선순위를 빼앗기지 말라. P0별 테스트와 실제 모바일 검증을 통과시킨 뒤 다음 단계로 이동한다.

3단계 — 고가치 P1 화면·플로우 구현:

P1-01 내 기록 상세·수정·삭제:
- /diary/[id]를 작성자 소유자 모드와 허용된 타인 조회 모드로 명확히 분리한다.
- 목록 카드에서 상세로 진입하고 수정·soft delete·복귀·캐시 무효화를 완성한다.
- 존재하지 않음, 삭제됨, 권한 없음을 구분한다.

P1-02 watchlist:
- 기존 찜과 watchlist의 관계를 결정하고 안전하게 마이그레이션한다.
- /watchlist, priority, memo, plannedWith, status와 중복 방지를 구현한다.
- 작품 상세에서 추가하고, watchlist의 봤어요 동작에서 선택 작품을 포함한 기록 작성으로 전환한다.
- 홈·프로필에는 작은 미리보기와 전체 화면 진입만 둔다.

P1-03 초대 코드 가입:
- 초대 코드 발급·만료·사용 횟수·발급자·사용자 모델과 API를 구현한다.
- 코드 검증과 사용자 생성을 원자적으로 처리하고 동시 사용을 테스트한다.
- /signup에 초대 검증 단계를 추가하고 가입 후 첫 작품 탐색으로 연결한다.
- 초대 정책과 통합되지 않은 소셜 로그인은 숨긴다.

P1-04 같이 본 경험:
- 가입 사용자 연결과 자유 입력 이름을 모두 지원하는 companion 모델을 구현한다.
- 장소, 분위기, 추억 메모를 작성·수정·상세 화면에 추가한다.
- 값이 없으면 상세 카드를 숨기고, 기록 공개 권한과 동일하게 보호한다.

P1-05 친구 관리:
- PENDING/ACCEPTED/REJECTED 관계와 요청 생성·수락·거절·취소·삭제를 구현한다.
- /friends에 친구, 받은 요청, 보낸 요청과 빈 상태 CTA를 제공한다.
- 중복 요청, 자기 요청, 양쪽 상태 불일치를 차단한다.

P1-06 친구 피드:
- 기존 /community를 친구 피드로 재편하거나 명확한 /feed route 전략을 선택한다.
- 수락된 친구의 FRIENDS 기록과 나에게 지정된 SELECTED 기록만 제공한다.
- 기존 카드, 스포일러, 댓글 UI를 재사용하되 댓글·반응 권한도 동일하게 검증한다.
- 친구 해제와 공개 범위 변경 시 상세와 캐시 피드에서 즉시 접근을 회수한다.
- 알림에서 대상 기록·댓글로 deep link한다.

4단계 — P2 PWA:
- manifest, 아이콘, display/start URL, service worker와 설치 안내를 구현한다.
- 오프라인 상태와 저장 실패를 정직하게 안내하고 입력을 유지한다.
- 초기 MVP에서는 자동 동기화를 가장하지 말고 재연결 후 명시적 재시도를 제공한다.
- Android standalone과 자가 호스팅 경로를 검증한다.

데이터·마이그레이션 규칙:
- 엔티티 변경에는 명시적 TypeORM migration, rollback 고려, 기존 데이터 보존 전략을 포함한다.
- PUBLIC, favorite, 기존 follow 관계를 새 모델로 옮길 때 데이터 손실과 과도한 공개가 생기지 않게 한다.
- 권한 판정은 UI 조건문이 아니라 서버 공통 정책으로 구현한다.
- soft delete, 관계 변경, 공개 범위 변경 후 캐시 무효화를 테스트한다.
- 실제 운영 DB에 migration을 적용하거나 배포하지 않는다. 로컬·테스트 DB에서 검증한다.

검증 규칙:

7. 실행한 테스트·build·브라우저 검증 결과
8. 갱신한 TODO와 재검증 문서 링크
9. 남은 blocker와 배포 전 주의사항
```

## 6. 프롬프트 쌍의 종료 조건

두 프롬프트를 모두 실행한 뒤 다음 상태를 목표로 한다.

- P0 미구현·부분구현·잘못된구현이 없다.
- 필수 P1/P2는 UI만이 아니라 API·DB·권한·테스트까지 완료됐다.
- 불필요한 공개 SNS 기능은 데이터 손실 없이 활성 MVP 동선에서 분리됐다.
- AS-IS의 Davas 브랜드와 모바일 카드 톤은 유지되지만 비동작·보안·접근성 결함은 제거됐다.
- `davas-high-value-screen-flow-todo.md`의 완료 표시마다 검증 근거가 있다.
- 운영 서비스는 변경하지 않았고 배포는 별도 검토·승인 단계로 남아 있다.
